# Lombok — Usage Rules

## Principle

Use Lombok to reduce boilerplate **only when it improves readability** and does not hide important domain behaviors.

## General Rules

- Use Lombok only if already adopted by the project or if its introduction has been approved.
- Prefer explicit, targeted annotations over overly broad ones.
- Do not use Lombok to mask anemic models, oversized classes, or confused responsibilities.
- Code generated by Lombok must remain understandable for those who read, test, and debug it.

## Recommended Annotations

- `@Getter`: to expose immutable fields or readable state.
- `@RequiredArgsConstructor`: for constructor injection with `final` fields.
- `@Builder`: for objects with many optional fields or readable test setup.
- `@Slf4j`: for logging, if the project standard requires it.
- `@NoArgsConstructor(access = AccessLevel.PROTECTED)`: for JPA entities when required by the framework.

## Annotations to Use with Caution

- `@Setter`: avoid indiscriminate public setters, especially on domain and entities.
- `@Data`: avoid on entities, domain classes, and complex DTOs; it generates getters, setters, equals, hashCode, and toString all together.
- `@EqualsAndHashCode`: explicitly define which fields to use, especially for entities with identity.
- `@ToString`: exclude sensitive fields, lazy relationships, large collections, and bidirectional references.
- `@AllArgsConstructor`: may expose unintentional constructors; prefer factories or builders when invariants are needed.

## Entities and Domain

- Entities must protect their invariants: avoid `@Data` and public setters on all fields.
- For entities with stable identity, `equals` and `hashCode` must not depend on mutable fields.
- Do not include bidirectional relationships in `toString`, `equals`, or `hashCode`.
- Prefer intentional domain methods (`activate`, `complete`, `cancel`) over generic setters.

## DTOs

- For immutable DTOs, prefer `record` when compatible with framework and serialization.
- If you use DTO classes, `@Getter`, `@Builder`, and targeted constructors are preferable to `@Data`.
- For request DTOs that require Bean Validation/Jackson, verify that constructors and accessors are compatible.

## Logging

- `@Slf4j` is acceptable if consistent with the project.
- Do not log secrets, tokens, passwords, connection strings, or unnecessary personal data.
- Avoid `System.out.println` and `printStackTrace`.

## Anti-Patterns

| Anti-pattern | Alternative |
|---|---|
| `@Data` on JPA entities | `@Getter` + domain methods + explicit equals/hashCode |
| `@Setter` on every domain field | Intentional methods that enforce invariants |
| `@ToString` on bidirectional relationships | `@ToString.Exclude` or explicit implementation |
| `@EqualsAndHashCode` with mutable fields | Stable identity or manual implementation |
| `@Builder` that bypasses validation | Private/factory builder that validates invariants |

## Checklist

1. Does the Lombok annotation make the code more readable?
2. Is the generated behavior obvious and safe?
3. Do `equals`, `hashCode`, and `toString` not include dangerous fields?
4. Are no setters exposed that violate invariants?
5. Do tests, serialization, and frameworks work with the generated constructors?
